# LLMskill-forChem 修改与优化基线

日期：2026-10-09

文档版本：1.0

整理时的代码基线：`6b1caa7`

## 1. 文档用途与状态

本文汇总两轮架构讨论及用户修正，作为后续设计、实施与审计的共同依据，防止范围和目标漂移。它是维护用基线，不替代面向使用者的 README。

本文区分已确定的约束、建议实施的方向与尚待验证的能力。列入规划不代表功能已经实现，也不代表上游能力已被本合集完整继承。具体技术选型可在这些约束内自主调整，不需要对每个实现细节重复征求意见；改变核心约束时应明确提出差异，并记录用户决定。

## 2. 已确定的目标与边界

- 核心目标是为化学与材料研究者提供省时、方便的技能使用方式；不预先承诺比原项目更高效或科学上更可靠。
- 可以附带工作流、验证案例、更新检查和其他必要设施，但必须保留单项 skill 的独立下载、安装与直接调用。
- 用户继续使用自然语言提问，或直接指定 skill。架构升级不增加新的 UI、任务菜单、表单、必经向导或要求用户手动选择 workflow 的步骤。
- “按科研问题组织”落实在内部能力目录、路由规则、工作流和案例中；现有技能名称和工具分类仍可使用。
- 优先继承上游设计，补充跨来源衔接与验证。设施的复杂度必须有具体任务收益和维护依据。
- 技能正文以英文为主，面向用户的说明以中文为主。保留原始英文名称和来源展示。
- 公共仓库只包含通用内容及可公开案例；个人课题、个人情况、机器路径、凭据和私人广播不进入公共内容。
- 本文不触发 README 定位改写，也不建立新的全局 agent 默认规则。

## 3. 当前基础与主要缺口

整理时仓库已有独立技能、来源记录、五类功能索引、通用 router、领域子路由、安装器、图形选择器和 DOI 分析路线。因此后续应渐进演进。

主要缺口包括：

1. 跨来源的任务适用范围、前置条件、技能关系和产物交接尚需统一表达。
2. 收录某个 skill 不等于收录其原项目的顶层规则、运行器、工具实现和 workflow；需审计实际依赖是否完整。
3. 安装与格式检查不能回答技能是否选对、任务是否完成、科学结果是否合格。
4. 上游更新需要同时处理版本、许可、支持文件、依赖和本地适配。
5. 推荐优先级需要任务适配与验证依据，不能由来源名气或任意全局分数决定。

## 5. 内部架构方向

### 5.1 保留可独立使用的技能底座

`skills/` 保持可单项分发，保留必要资源、许可和来源。单项使用不强制依赖面板、后台服务、数据库、模型 API 或整个合集运行器。

安装技能不等于安装或执行科学软件。外部软件、密钥、计算资源与运行许可应明确列为依赖，不能将安装完成写成任务可运行。

### 5.2 统一能力说明，保留上游正文

优先扩展现有 `catalog.json`；来源沿用 `SOURCE.json`。具体字段在实施时精简设计，但应能表达：

- 可完成的任务、适用与不适用情况。
- 所需输入、预期产物及运行条件。
- 前置、后续、替代和领域分派关系。
- 对应验收案例、实际验证环境及已知限制。
- 上游版本和本地适配依据。

中文索引、router 索引和面板展示尽量由共同来源生成，避免多套手工目录。不要为了统一外观批量重写上游正文。

### 5.3 增强现有 router，保持职责分层

内部路线：自然语言请求 → 识别任务与输入 → 检查约束及候选 → 单项技能或适用 workflow → 领域 router/具体技能 → 产物检查与实际执行记录。

通用 router 处理跨领域选择；领域 router 保留内部专长。例如 `dft-vasp` 继续分派 VASP 子任务，不在通用 router 重复维护整套细节。防止循环调用与多个 router 相互争夺任务。

简单任务直达单项技能；复杂任务按需读取对应路线。目录中的优先级只是选择依据，不应宣称它天然获得宿主强制权重或保证自动触发。单项直接指定仍可绕过合集编排。

### 5.4 Workflow 负责衔接与验收

先查上游已有路线：适用则复用；依赖完整原项目则明确依赖并评估成本；确有跨来源缺口再补充。

每条路线应说明输入、进入条件、候选技能、交付产物、验收方法和失败分支。可以先用 Markdown 操作说明、少量结构化定义和必要检查脚本实现；需要计算调度时优先接入成熟引擎。

第一批建议覆盖：

| 通用任务 | 关键产物 | 必须覆盖的失败情形 |
| --- | --- | --- |
| 单篇论文阅读与证据分析 | 论文身份、带位置的证据、分析及缺失材料 | 无全文、元数据冲突、缺少补充材料 |
| VASP 算例检查与故障诊断 | 完成状态、异常证据、修改建议、结果可用性 | 未收敛、被中断、文件不完整或证据不足 |
| 科研表格检查与分析 | 数据质量结果、适当分析与图表、适用限制 | 缺失或异常数据、单位或分组不清、分析条件不满足 |

路线由模型在现有调用路径中使用，无需增加用户操作。无法完成某一步时明确限制后续结论；例如读出能量不等于该能量可作为合格训练标签。

## 6. 案例与证据是主要新增内容

每个案例尽量包含：可公开输入、自然语言请求、允许的技能路线、需避免的误用、预期产物、检查方法、实际版本与环境、结果及限制。

允许多条合理路线，不用固定调用顺序代替任务正确性。区分示例、已运行案例和回归测试；没有运行的内容不得标为验证通过。

验证分三层：

1. **路由验证**：是否选择合适技能，有无误触发或不必要调用。
2. **执行验证**：依赖、脚本、工具和交接是否正常。
3. **科研结果验证**：产物是否满足该任务的科学判据。

优先加入正常、缺输入和失败案例。检查器应使用独立参考或明确的可验证条件，并证明能识别典型错误；不能仅让另一个模型评价回答是否完整。

比较 workflow/router 的收益时，固定模型、环境、工具和技能版本，比较直接调用与增加编排后的表现。研究技能本身收益时另设有无技能对照。记录任务正确性、人工纠正次数、耗时与 token，并注明重复次数及样本局限。不得把安装测试、单次演示或上游评测直接写成本合集的科学性能证据。

## 7. 技能选择与优先级

初期使用透明规则，不设置缺乏数据支持的全局评分：

1. 尊重用户指定和项目明确约束。
2. 检查输入、授权与执行条件；区分可执行和只能提供指导。
3. 按任务与产物匹配候选。
4. 优先参考相似任务、相似环境中的验证证据。
5. 比较额外依赖、联网、费用和上下文成本。
6. 同等条件采用稳定默认项，并记录切换条件。

例如 `lit-review` 与 `literature-review` 先按创新性审计和一般文献综合等适用范围区分，不随机选择、不无条件叠加。数据积累充分后才评估数值权重或学习排序；未验证应明确标记。

## 8. 更新、发现与优化的共同验证流程

### 上游更新

发现新版本 → 比较上游旧版、上游新版与本地适配 → 检查许可、支持文件和依赖变化 → 找出受影响路线与案例 → 候选版本验证 → 形成可审查变更 → 发布固定版本。

不得静默覆盖用户修改或让已安装环境跟随上游漂移。保留版本、备份和回退依据。现有来源记录格式如有差异，应先兼容或迁移，不能假定所有技能均有相同哈希结构。

### 主动发现

从案例暴露的能力缺口出发，整理候选的用途、许可、重叠、证据和维护成本。候选可以先作为外部推荐链接，未经核查不自动批量收录。高 star、知名作者和论文发表情况属于检索线索，不是任务质量评分。

### 技能优化

失败案例 → 定位路由、依赖、交接或技能问题 → 针对性修改 → 原案例与其他独立案例验证 → 更新推荐依据。

优先调整合集自有说明与衔接；必要的上游修改保留差异和来源。不能通过针对公开验收答案修改技能制造提升，也不能由模型自行评分后自动发布“优化版”。

## 9. 附属设施的边界

- 执行记录只记实际技能、版本、操作、产物、状态和公开可观察的选择依据，不要求内部思维链。合集组合任务保留结果前缀；单项直接调用不强制附加。
- 项目参数、赝势约束和目录习惯由用户项目配置提供，优先于通用建议；私人配置不混入公共技能。
- 环境检查针对当前任务，避免每次扫描全部科学软件。
- 已知有问题的技能可退出默认推荐，并保留限制、替代项及回退说明。
- 按需读取短索引、选中技能和所需参考资料，不全量加载正文。
- 文件与安装工具继续兼顾 Windows/Linux；宿主发现、工具执行和科学软件平台支持分别验证。DSH 未测试的部分继续如实标注。
- 优先使用现有命令行工具与本地文件，不预先引入常驻服务、数据库、自研调度器或新的多代理系统。

## 10. 实施顺序与完成标准

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| 0. 上游依赖与架构审计 | 检查已收录技能需要的外部规则、运行器、工具及 workflow | 明确哪些已继承、哪些缺失、哪些必须外部提供；不猜测兼容性 |
| 1. 能力与衔接整理 | 扩展目录、明确关系、复用或补充首批路线 | 自然语言和单项调用保持原体验；关键输入输出与失败分支可检查 |
| 2. 案例与证据 | 建立正常、缺输入和失败案例，分层记录验证 | 路由、执行和科学结果的结论有各自依据；不以打包检查替代 |
| 3. 更新维护 | 候选更新、许可和依赖检查、关联回归、版本回退 | 更新可追溯，不静默覆盖本地适配 |
| 4. 按证据改进 | 能力缺口发现、推荐调整、技能适配验证 | 新增内容能指出具体任务收益及代价；保留未验证与失败记录 |

各阶段可围绕一个任务纵向完成，再扩展其他任务，避免先建设大量空目录和无人使用的抽象层。首批三类任务属于建议范围，不构成必须一次全部实现的要求。

## 11. 每轮修改的防漂移检查

提交或报告修改前核对：

- 本轮解决了什么具体问题？是否有案例或依赖审计依据？
- 是否增加用户必须理解的概念、点击、表单或选择步骤？如有，应重新设计。
- 是否先检查了上游已有实现？复用了什么，为什么必须新增？
- 单项 skill 是否仍可独立获取和使用？
- 是否保留名称、原文、许可、来源与本地修改记录？
- 是否引入重复维护的信息、无证据排序或过重依赖？
- 检查证明了哪一层能力？还有哪些未验证？
- 是否误把规划、示例或上游证据写成本项目已实现、已验证的成果？
- 是否改动了未被要求变更的 UI、全局 agent 规则或公共定位？

如后续决定改变本基线，应记录日期、变更条目、原因及用户决定。正常实施细节无需反复确认；冲突时以用户更新的明确要求为准。
